## 1. The shim swap, wrapped (`8a6dc71e34`)

`linux/scripts/swap-shim.sh` + `linux/tests/swap-shim-smoke.sh` (24/24).

The thing that must survive: **the swap is a rename, never an
overwrite.** A live cmux-adw MAPS `libghostty-gtk.so`; changing those
bytes in place SIGBUSes it. So the installed file is renamed to
`libghostty-gtk.so.pre-<utc>` FIRST — the running process keeps its
inode under the new name — and only then is the new file renamed into
the freed path. Everything else in that script is downstream of this one
fact.

Guards, each with a reason: self-hosting check BEFORE any mutation (else
promote.sh's own guard fires after the swap and leaves the operator
half-done); export-regression refusal (a shim missing a symbol the
installed one has is a downgrade or a broken build); dlopen verification
in a throwaway python3 process with RTLD_NOW plus a lookup of the
symbols cmux resolves (stricter than ldd, and a crash cannot hurt the
caller) applied BEFORE installation and again after, with automatic
rollback; same-filesystem and staleness checks.

**State: not activated, by choice.** The new shim (with
`ghostty_embed_surface_pid`) sits at `ghostty/zig-out-dev/lib/`, inode
26015657. The canonical `ghostty/zig-out/lib/libghostty-gtk.so` is still
inode **17049392, mtime 2026-07-22**, and PID 14071 maps it. Because
cmux resolves the accessor by dlsym, a promote without the swap is safe
— pid attribution just stays dark. Run `swap-shim.sh` from OUTSIDE the
daily when hias chooses.

## 2. Notification semantics — the finding, and the decision I made

A sibling desk sent `cmux notify --workspace <mine>` believing it would
inform this session. It informed hias (tab badge + GNotification over
D-Bus, suppressed only when the window is focused / that workspace is
active / the panel is open) and reached no agent at all. Notifications
are a human-attention channel; there is no agent inbox and nothing
polls. The session channel is a feed letter (`feed.push` into a stable
workstream) plus a pane doorbell.

The deeper find (`38a6dc7720`): the SHARED CLI sends `--workspace` with
no `--surface` as `notification.create_for_caller`, carrying the target
workspace AND the caller's own surface. macOS's resolver applies issue
**#7939** — a surface not in the named workspace outranks it and the
notification follows the surface home — so on macOS that command
notifies the SENDER. Our port stores the surface unchecked instead.

**Decision (mine, against the passkey desk's vote), reasoning worth
keeping:** #7939's rule is RIGHT for the case it was written for (a
moved pane whose agent env still names the old workspace). The defect is
upstream of the resolver: the CLI packs "the workspace I was spawned in"
(stale, should lose) and "the workspace the human typed" (authoritative,
should win) into ONE parameter, so the resolver cannot tell them apart.
Fix = implement #7939 here + validate membership, AND change the shared
CLI to not attach the caller's surface when `--workspace` is explicit
(upstream candidate, fixes macOS too). Rejected alternative: drop the
resolver rule so explicit `--workspace` always wins — trades one real
fix for another. Recorded in GAPS with both sides.

## 3. Flatpak reads a config file nobody edits (`adce6eedc8`)

Measured inside the installed app, not inferred from the manifest:

    HOME=/home/hias                                   <- real home
    XDG_CONFIG_HOME=/home/hias/.var/app/com.manaflow.cmux/config
    host  ~/.config/cmux/cmux.json    -> readable, 88 bytes
    app's $XDG_CONFIG_HOME/cmux/…json -> No such file or directory

`$HOME` stays real under `--filesystem=home`, but the XDG variables do
NOT follow it. `Settings.swift` prefers `XDG_CONFIG_HOME`, so **the
Flatpak has been running on defaults**, ignoring a config it can read.
Split-brain: the host-CLI wrapper runs the binary outside the sandbox
(where `XDG_CONFIG_HOME` is unset) and therefore reads the host file.

**Awaiting hias's call:** prefer `$HOME/.config/cmux/cmux.json` under
`FLATPAK_ID` (one human, one config) with a per-app file winning as an
explicit opt-out — vs the sandbox-purist option of documenting the
per-app path. This blocks the passkey desk's plan to flip
`CMUX_WEBAUTHN` via settings.

Adopted from that desk, now a packaging rule in features/15: a
consent-bypass env var (`CMUX_WEBAUTHN_AUTOAPPROVE`) must NEVER appear in
a manifest, override recipe or desktop entry.

## 5. One correction to the safeguard request itself

"Executing a binary deleted underneath it by a rebuild (198 mappings
marked deleted)" is EXPECTED and harmless on this stack, not evidence of
danger: `swift build` replaces the binary on disk and the running
process keeps its inode — that is exactly why building is always safe
from inside cmux (docs/linux-port/INSIDE-CMUX.md). The spinning main
thread is a real symptom; the deleted mappings are not.
