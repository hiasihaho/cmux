# Dogfood report

## Summary
Using only cmux browser verbs I extracted **all 563 poses** (name, Sanskrit names incl. devanagari, category, subcategory, difficulty, description, benefits) from the pocketyoga Vue SPA: 167 from the index page's client store, 479 after driving the real search box through an a–z sweep, and closure to 563 by crawling 85 detail pages with `goto`+`wait`+`eval` (54 s total, ~0.64 s/page). Score against the oracle: **563/563 matched, 0 missed, 0 spurious, 562/562 descriptions**; 552 records match on every compared field, 11 differ only in `difficulty` because the app itself displays "advanced" where its data file says "expert". The tool is genuinely capable of this job — the two real dangers found are a stale-document race after `goto` and quadratic CPU burn on `eval` results above ~2 MB.

### Focus answers
- **Settle detection** — solved, no sleeps needed, but with a trap. `wait --function` polls an arbitrary JS expression: `cmux browser --surface surface:4 wait --function '(function(){if(location.pathname!=="/pose/Tree")return false; var s=document.querySelector("section.mainProduct"); return !!(s&&s.__vue__&&s.__vue__.pose&&s.__vue__.pose.name==="Tree")})()' --timeout-ms 20000` returns OK the moment the predicate is true, rc=1 with `Error: timeout: Condition not met before timeout` otherwise. For XHR refetches without navigation (the search box) I waited on app state: `wait --function '... !d.loading && d.lastFetch.indexOf("search=a")>=0 ...'`. **The trap:** `goto` returns OK before the new document exists, and a subsequent `wait`/`eval` runs against the *stale previous page*. A predicate that could be true on the old page passes instantly — this bit me twice (details in Bugs). The fix is to make the predicate provably new-page-only (check `location.pathname` *and* target-specific content). `readyState` was indeed useless.
- **Scale** — `eval` never truncated or errored; it degrades by CPU instead. Worked: 264 KB in 0.8 s, 738 KB in 0.93 s, 2 MB in ~1 s. Then it turns quadratic *in the `cmux` CLI process* (wall ≈ user CPU): 3 MB = 11.3 s, 8 MB = 78.6 s, 32 MB projected ~20 min (killed). Largest comfortable result: **2 MB**; smallest painful: **3 MB**. Killing the CLI mid-transfer did not harm the surface — the next `eval` worked immediately.
- **Quoting** — unproblematic throughout. Single-quoted bash with double quotes inside JS worked; CSS attribute selectors with embedded quotes survived: `cmux browser --surface surface:4 get count --selector 'a[href$="/pose/Tree"]'` → `1`. Multi-line programs pass fine via `eval --script '<newlines allowed>'`. Two conventions to know: a JS exception returns rc=1 with `Error: js_error: ReferenceError: …` (clean); returning a raw object gets re-serialized as pretty-printed JSON with **key order not preserved** — return `JSON.stringify(...)` yourself for stable output; `undefined` comes back as the literal string `undefined` with rc=0.
- **Missing primitives** — (1) a navigation barrier: `goto --wait-selector <css>` / `--wait-function <js>` so the stale-document race is impossible to hit; today `--snapshot-after` presumably races the same way. (2) `eval --file <path>` (or stdin): everything must be inlined into shell strings, painful beyond one-liners. (3) a way to raise snapshot's ~110-char node-text truncation (`--full-text`); descriptions were cut mid-word, forcing `get text`/`eval` for anything long.
- **Lies** — one real class: post-`goto` staleness. `wait` and `eval` report success while silently operating on the previous document (see Bugs #1). Also one transient 20 s `wait` timeout on a page that loaded fine on retry (flaky network, not a tool lie), and `console list` prints a bare `OK` for an empty log, which is ambiguous until you learn it.

## Works
- `browser open <url> --workspace workspace:3` into a background workspace: zero focus disturbance to the human's session for the entire run, including 85+ navigations and a screenshot.
- `wait --function` / `--selector` with `--timeout-ms`: correct OK/rc=1 semantics, instant return on already-true predicates; carried the whole run with **zero sleeps** in the final pipeline.
- `fill --selector ".search-bar input" --text "rag doll"` triggered Vue reactivity properly — the app debounced, refetched (`lastFetch: "?sort=category&search=rag%20doll"`), and re-rendered. Many automation stacks fail exactly here.
- `eval` payloads up to 2 MB round-trip fast and byte-exact (validated by parsing 688 KB and 738 KB dumps); JS state persists between calls on the same document, so an in-page accumulator (`window.__qaPoses`) across 26 search queries worked.
- The 85-page crawl: `goto` → strict `wait --function` → `eval` at ~0.64 s per pose page, 84/85 first-pass success, the one timeout succeeded on retry.
- `get text --selector 'section.mainProduct'` returns clean full text (complete descriptions); `get count`/`get attr` distinguish 0-matches from not-found sensibly; `snapshot` (3.3 KB on a detail page) is a good cheap map of the page; `screenshot --out` produced a correct 120 KB PNG; `console list` captures `console.log` including object args.
- Error surfaces are honest: `js_error` with the real message on throw, `not_found` naming the selector, `timeout` on wait.

## Bugs
1. **`goto` returns before navigation; `wait`/`eval` run against the stale document.** Repro: be on page A (`/pose/`), then `cmux browser --surface surface:4 goto https://pocketyoga.com/pose/RagDoll` → `OK` immediately; instantly follow with `cmux browser --surface surface:4 wait --function '(function(){var s=document.querySelector("section.mainContent"); return !!(s&&s.__vue__)})()'` → passes in 0.117 s against page A; an `eval` right after reported page A's components. Second repro: after `goto .../pose/WideLeggedForwardBendIVPreparation`, `eval 'location.pathname'` returned `/pose/HeadToKneePreparation` (the previous page). Expected: either `goto` blocks until the document is committed, or the docs/verbs make the race impossible (`goto --wait-…`). Actual: success is reported while the old page is still live, which converts into silent wrong-data extraction if the predicate isn't new-page-specific.
2. **`eval` result transfer is quadratic in size, CPU-bound in the CLI.** Repro: `time cmux browser --surface surface:4 eval '"x".repeat(N)'` → 2 MB ≈ 1 s, 3 MB = 11.3 s, 8 MB = 78.6 s (user ≈ wall, so the client process is burning it), 32 MB unbounded (killed after 2 min). Expected: roughly linear transfer — 8 MB should be ~4× the 2 MB cost, not ~80×. No error and no truncation is arguably worse: it looks like a hang.
3. **`snapshot` truncates node text at ~110 chars with no override.** Repro: on `/pose/Tree`, `snapshot` shows `…rooted into the inner thi` cut mid-word. Expected: a flag to get full text; actual: none, must fall back to `get text`/`eval`. (Friction, not corruption.)
4. Minor: `console list` on an empty log prints just `OK` — indistinguishable at a glance from "command did nothing"; an explicit `(no entries)` would remove the ambiguity.

## Suggestions
- Add a navigation-barrier option to `goto`/`back`/`forward`/`reload` (`--wait-selector`, `--wait-function`, or at minimum block until the new document is committed) — it's the single change that removes this run's biggest hazard.
- Add `eval --file`/stdin, and fix the superlinear result transfer (or document a practical size limit and stream beyond it).
- Site quirks, for anyone repeating this: the app's full dataset sits in client memory on any detail page (`section.mainProduct.__vue__.posesData`, 563 poses, one 714 KB eval); its variation lists contain two dead references the app itself 404s (`SeatedOnHeelsPrayerClosedEyes`, `TreeClosedEyes`); and the detail view remaps difficulty `expert`→`advanced`, so DOM-level scraping "faithfully" captures 11 values that disagree with the data file.
